# ChatGPTチャットモードで進める新規比較記事手順

## 目的

ChatGPTの**チャットモード**には、商品選定と情報調査だけを依頼する。Workモードへ依頼しない。記事データへの登録、テンプレート適用、表示検証、公開判断はCodex側で行う。ChatGPTに記事作成やサイト変更を任せない。

## 1. ChatGPTへ送る依頼

毎回、商品選定から始める完全新規の依頼を送る。過去記事、過去の調査結果、「前回の結果を補う」といった前提は使わない。調査結果に不足・矛盾・URL形式不備が1つでもあれば、その結果は破棄し、商品選定から同じ完全新規手順をやり直す。部分修正で記事化へ進めない。

商品選定の段階では、公式情報、公式画像、商品ごとのAmazonまたは楽天の商品詳細ページを確認できる候補を選ぶ。ChatGPTには成果用アフィリエイトURLの取得を要求しない。楽天の成果URLはCodex側の楽天Ichiba API（Application ID・Access Key・Affiliate ID）で商品詳細と`affiliateUrl`を取得する。APIが利用できない場合だけ、楽天ボタンを保留し、ユーザー提供URLがあれば追加する。SNSは採用投稿が0件でも記事化を妨げない。埋め込みが確認できない場合でも、直接投稿URLを確認できれば参考リンクとして採用できる。

調査結果の判定は、必須項目と任意項目を分けて行う。ChatGPTから受け取る必須調査データは、公式ページ・公式画像・正式名称/型番・公式比較仕様・商品ごとのAmazonまたは楽天の商品詳細URL。AmazonのアフィリエイトURLはCodex側で確認済みASINから生成・検査し、楽天のアフィリエイトURLはCodex側で楽天APIから取得・商品一致を検査する。APIが利用できない場合の楽天成果URLの未取得は、商品選定をやり直す理由にしない。SNSの0件とSNS埋め込みの未確認も任意項目とする。`articleReady` は、記事に表示する購入ボタン用のURLが揃った時点でCodex側が判定する。

次の文章をそのままチャットモードへ送る。

```text
比較記事に使う調査データを作成してください。記事本文やサイトコードは作成せず、商品選定と調査結果だけを返してください。

1. 既存記事と検索需要が重複しにくく、比較する価値がある商品A・Bを同じカテゴリから選ぶ。
2. 商品A・Bの正式名称、型番、メーカー公式商品ページURL、公式画像URLを確認する。
3. メーカー公式ページだけを根拠に、共通仕様、主な違い、公式価格（確認日付き）を調査する。
4. 楽天市場とAmazonで各商品の商品詳細ページを探し、商品名・型番が一致する実URLを示す。Amazonは商品ページURLとASINを確認する。Amazonのタグ付きURLはCodex側でASINから生成・検査するため、ChatGPT側で成果URLを作る必要はない。楽天は商品詳細URLを確認する。楽天の成果URLはCodex側が楽天Ichiba APIの`affiliateUrl`から取得するため、ChatGPT側でログイン画面を操作したり成果URLを推測したりしない。
5. X、YouTube、Reddit、TikTok、note等から実利用者の感想を探す。商品名またはシリーズ名で広く検索し、型番完全一致を必須にしない。ただし別モデル・旧世代・企業・メーカー提供・PR・広告・アフィリエイト投稿は分けて記録し、採用投稿と混同しない。元投稿を直接確認できたURL、投稿者、投稿日、商品一致の根拠、実利用の根拠、感想の要約、広告・PR判定を記載する。採用件数が0件でも、見つかった候補と除外理由を示す。SNS投稿が見つからなくても、公式情報と購入先が揃っていれば `articleReady: true` とする。埋め込みは確認できた投稿だけに設定し、直接投稿URLがあれば埋め込み未確認でも採用候補として渡す。
6. 最後に、記事へ渡せる構造化データを出す。採用SNS投稿がない場合はSNS欄を空配列にする。推測でURLや仕様を補わない。JSONの判定は次のとおりにする。
   - `articleReady` はCodex側が判定する。公式ページ・公式画像・商品同定・公式比較情報・記事に表示する購入ボタン用URLが揃った場合だけ `true` にする。
   - ChatGPTのJSONでは、調査不足だけを `restartRequired: true` とし、楽天成果URLの未取得だけを理由に商品選定をやり直さない。
   - SNSが0件、SNS埋め込みが未確認の場合は `unconfirmedItems` に理由を書き、記事側で該当欄を非表示または直接リンク表示にする。

調査日（JST）、確認できなかった項目、除外理由を必ず明記してください。回答は「商品選定」「公式情報」「販売・アフィリエイトURL」「SNSの感想」「記事用JSON」の見出しで分けてください。
```

## 2. 受け取った結果の確認

- 商品A・Bの公式ページを実際に開き、名称、型番、仕様、画像を再確認する。
- 販売URLは商品詳細ページの一致を確認する。ストアID、検索結果URL、推測URLは採用しない。
- SNSは採用と除外を分ける。採用0件の場合、SNS見出し自体を記事に表示しない。
- SNSの投稿数が少ないことを「言及者がいない」と解釈しない。検索範囲と除外理由を明記する。

## 3. Codexでの記事化

`docs/article-research-template.md` の台帳を埋め、`CommercialArticleSeed`へ結果を移す。記事本文には確認日を表示し、SNSの直接リンクと埋め込み対象を分ける。購入先は商品カード内に楽天・Amazonの同一スタイルのボタンを置き、重複導線を作らない。さらに `docs/article-handoffs/<handoffManifestId>.json` にChatGPTの最終調査結果と採否を記録し、seedの `handoffManifestId` と一致させる。参照記号（`turn...`、`sourceRef`）はURLとして使わず、必ず`https://`で始まる実URLを記録する。

### テンプレート固定ルール

- 新規記事のページラッパーは必ず `CommercialArticlePage` を使う。`pnpm article:add` の出力を手書きで旧形式へ戻さない。
- `ArticleComparisonPage` は過去記事の互換表示専用。既存の互換ページは変更せず、新規記事へコピーしない。
- `pnpm verify:lint` のテンプレートポリシー検査で、許可リストにない新規の旧テンプレート使用を止める。
- レイアウトを変更するときは現行テンプレートとこの手順書を同じPRで更新し、過去記事の互換コードは別の変更として扱わない。

### 現行テンプレートの表示順（2026-09-17）

新規記事は必ず次の共通構成にする。過去記事の見た目や古いテンプレートを参照して新規ページを組み立てない。

1. 結論（左右の商品カード）
2. 主な比較ポイント（勝っている側を各行でハイライト）
3. よくある質問
4. 購入先（商品画像カードの中にAmazon・楽天ボタン。確認できたリンクだけ表示）
5. SNSでの感想（採用投稿がある場合だけ表示。投稿がなければ見出しも検索リンクも表示しない）
6. 更新履歴・情報源

ページ上部の目次は横並びリンクではなく、枠で囲った見出し付きの`<ol>`にする。目次の順番と本文の順番を一致させる。「30秒でわかる」「次にすること」「迷ったら、ここから決める」「公式情報（確認できた項目）」「詳細仕様（公式ページで確認した項目）」の見出しは新規記事で使用しない。SNSは採用URLを直接確認できた場合だけ埋め込みまたは投稿リンクを表示し、0件を空の見出しで残さない。

購入先は商品カードを1つずつ置き、カード内に同じ見た目のAmazon・楽天ボタンを並べる。Amazonは商品URLまたはASINと`kuraberuprodu-22`を使う。楽天の商品詳細アフィリエイトURLを確認できない場合は楽天ボタンを出さず、Amazonだけを表示する。ストアIDだけ、検索結果URL、推測URLは登録しない。

## 4. 公開前ゲート

1. `pnpm verify` がPASS。
2. 生成HTMLで目次の`<ol>`、商品名、型番、公式画像、比較行のハイライト、Amazonボタン、楽天ボタンの有無、SNS欄の表示条件を確認。
3. ブランチ、PR、必須チェックPASS、merge SHA確認の順で進める。
4. 明示的な公開承認後、`main`のmerge SHAを指定してProductionへデプロイする。
5. 2つの本番URLをHTTP 200で取得し、本文・画像・CTA・SNS表示を直接確認してから公開完了と報告する。

### 調査結果の反映ゲート

`pnpm verify:lint` の `check-article-handoff.mjs` が、現行記事のChatGPT調査記録と記事データを突合する。公式ページURL・公式画像URL・商品ごとに1つ以上の確認済みアフィリエイト先・SNSの採否を調査記録に書かず、また記録したURLをseedへ移していない場合は検査で停止する。楽天は任意項目で、未確認でもAmazon等の必須リンクが確認済みなら停止しない。SNSを採用する場合は直接投稿URLを必須とし、埋め込みは確認できた場合だけ使用する。記事用JSONに`turn...`や`sourceRef`が残っている場合も停止する。調査結果を「なし」とする場合も、未確認なのか採用対象なしなのかをmanifestに明記する。手順書の確認だけで公開へ進めてはいけない。
